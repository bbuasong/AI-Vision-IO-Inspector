# VLAD_Ops 이미지 흐름 비교 및 판단 기준 (2026-06-11)

## 목적

기준 이미지 저장, 검사 시점 이미지 캡처, AI 판정, 결과 이미지 저장의 기준을 기존 `VLAD_Ops`와 현재 `AI-Vision IO Inspector` 구조를 비교해서 정리한다.

판단이 필요한 부분은 기존 코드와 현재 코드의 차이를 먼저 확인하고, 어떤 기준으로 결정할지 명시한다.

## 기존 VLAD_Ops 이미지 흐름

### RTSP/CAM 모드

기존 `VLAD_Ops`의 핵심 흐름은 실시간 프레임 콜백 기반이다.

```text
카메라 Thread 시작
  -> VLAD_Rtsp_Info_Client_Registration
  -> VLAD_Ops_RTSP_Frame_Proc callback
  -> display 포인터를 OpenCV Mat로 래핑
  -> VLAD_Inference_Mat 호출
  -> valid count / detection data 확인
  -> 결과 draw 및 monitoring frame 갱신
  -> event 조건이면 이벤트 이미지 저장
```

확인된 특징은 다음과 같다.

- 프레임은 파일로 먼저 저장한 뒤 AI에 넘기는 구조가 아니라, 콜백으로 받은 메모리 프레임을 바로 `VLAD_Inference_Mat`에 넘긴다.
- `valid_cnt <= 0`이면 별도 이벤트 저장 없이 지나가는 흐름이다.
- `valid_cnt > 0`이면 draw, monitoring 갱신, event 처리 흐름이 실행된다.
- 이벤트 이미지는 현재 실행 디렉토리 아래 `Event`, `Original` 폴더에 저장하는 구조다.
- 제품별 기준 이미지 DB를 관리하거나, 기준 이미지와 현재 이미지를 직접 비교하는 흐름은 확인되지 않았다.

### File 모드

기존 파일 모드는 테스트용 이미지 폴더를 입력으로 읽고, 결과 이미지를 출력 폴더에 저장한다.

```text
IMAGE_PATH 이미지 읽기
  -> OpenCV Mat 생성
  -> VLAD_Inference_Mat 또는 Site별 Inference 호출
  -> InferenceData Draw
  -> OUTPUT_PATH에 결과 이미지 저장
  -> class count 변화로 Good/Bad 판단
```

주의할 점은 다음과 같다.

- `OUTPUT_PATH`가 이미 있으면 시작 시 폴더를 삭제하는 로직이 있다.
- 이 방식은 테스트 출력 폴더에는 사용할 수 있지만, 현재 프로젝트의 `DB\Image` 또는 `DB\History`에는 그대로 적용하면 안 된다.
- 기존 File 모드의 Good/Bad는 기준 이미지와 픽셀 비교가 아니라 class count 결과 변화 기준에 가깝다.

### HD DLL 측정 흐름

`HD_Dll` 쪽에서는 detection 결과의 crop 영역을 이용해 mask, contour, circle 등을 계산하고 `Thick` 같은 값을 화면에 draw하는 처리가 확인된다.

다만 확인된 범위에서는 다음이 보이지 않는다.

- 품번별 DB 기준값과 허용값을 읽어 비교하는 로직
- 길이/너비/높이/두께 전체를 현재 프로젝트 기준으로 판정하는 로직
- 등록 기준 이미지와 현재 이미지를 직접 비교해서 Pass/Fail을 결정하는 로직

따라서 기존 VLAD/HD 코드는 “영상에서 AI/비전 결과를 추출하고 표시하는 엔진”에 가깝고, 현재 프로젝트가 요구하는 “품번별 기준값/허용값 기반 최종 판정”은 별도 애플리케이션 로직으로 관리하는 것이 합리적이다.

## 현재 프로젝트 이미지 흐름

현재 `AI-Vision IO Inspector`의 공식 검사 흐름은 버튼 또는 PLC 신호에 의해 시작되는 일회 검사 흐름이다.

```text
검사 시작
  -> InspectionWorkflowService.RunInspection
  -> ICameraService.CaptureAll
  -> 촬영 이미지를 DB\History에 저장
  -> IAiInferenceService.Inspect
  -> VLAD_Inference_Mat 또는 시뮬레이션 AI 호출
  -> MeasurementService에서 기준값/허용값 비교
  -> JudgmentService에서 최종 Pass/Fail 판정
  -> UI와 이력 저장소 갱신
```

현재 기준 이미지 흐름은 별도로 관리한다.

```text
기준 이미지 저장 / 현재6개저장
  -> 버튼을 누른 순간 활성 카메라 프레임 캡처
  -> DB\Image\분류코드\품번 아래 위치별 기준 이미지로 저장
  -> 기존 이미지가 있으면 OldVer 백업 후 교체
```

즉 현재 프로젝트에서 이미지는 두 종류로 나눈다.

| 구분 | 저장 위치 | 목적 | 자동 삭제 여부 |
| --- | --- | --- | --- |
| 기준 이미지 | `DB\Image` | 품번별 기준/가이드 이미지, 향후 AI 정합성 기준 | 단일품목 삭제/교체 등 명시 동작 외 자동 삭제 금지 |
| 검사 캡처 이미지 | `DB\History` | 실제 검사 시점 증빙 이미지, 이력 확인 | 보관 기간/HDD 여유 공간 정책으로만 삭제 |

## 기존 방식과 현재 방식 비교

| 항목 | 기존 VLAD_Ops | 현재 프로젝트 | 판단 |
| --- | --- | --- | --- |
| 검사 트리거 | RTSP callback 중심의 실시간 처리 | `검사 시작` 시점의 일회 검사 | 현재 요구사항상 버튼/PLC 신호가 공식 검사 시점이므로 현재 방식 유지 |
| AI 입력 | 메모리 Mat 프레임 직접 입력 | 캡처 파일을 Mat로 변환 후 입력 | 추적성 확보에는 현재 방식이 유리하지만, 성능이 필요하면 Mat 직접 입력 경로를 추가 검토 |
| 기준 이미지 | 제품별 기준 이미지 DB 흐름 확인 안 됨 | `DB\Image`에 제품별 기준 이미지 관리 | 현재 프로젝트 요구사항이므로 유지 |
| 이벤트 이미지 | defect/event 발생 시 저장 | 모든 검사 시점 이미지를 History 저장 | 초기 양산 안정화 전에는 전체 저장이 추적성에 유리 |
| 판정 기준 | valid count, class count, site별 draw/처리 | AI 결과 + DB 기준값/허용값 비교 | 현재 프로젝트의 품번별 검사 요구에 맞음 |
| 출력 폴더 삭제 | File 모드 시작 시 OUTPUT_PATH 삭제 | 기준/이력 이미지는 자동 삭제 금지 | VLAD 방식 그대로 적용 금지 |

## 결정 기준

### 1. 공식 검사 시점

공식 검사 시점은 RTSP 프레임이 들어오는 모든 순간이 아니라 `검사 시작` 버튼 또는 향후 PLC 검사 시작 신호가 들어온 순간으로 한다.

이유:

- 사용자가 검사 시점을 명확히 통제할 수 있다.
- History 이미지와 검사 결과가 같은 시점으로 묶인다.
- 검사 이력, CSV 저장, DB 추적성을 보장하기 쉽다.

### 2. 기준 이미지 저장

기준 이미지는 검사 결과 이미지가 아니라 품번 마스터 데이터로 본다.

따라서 기준 이미지를 바꾸는 동작은 다음처럼 명시된 경우로 제한한다.

- 단일품목 등록에서 기준 이미지 삭제 버튼을 누르는 경우
- `현재6개저장` 또는 `기준 이미지 저장`으로 새 기준 이미지를 저장하는 경우
- 작업자가 폴더에서 수동으로 관리하는 경우
- 검사 중 기준 이미지가 없는 제품으로 확인되어 사용자가 기준 이미지 저장을 명시하는 경우

그 외 프로그램 내부 로직이 기준 이미지를 임의로 삭제하거나 덮어쓰면 안 된다.

### 3. 검사 캡처 이미지 저장

검사 캡처 이미지는 실제 검사 시점의 증빙 데이터로 보고 `DB\History`에 저장한다.

현재 권장 경로는 다음과 같다.

```text
DB\History\yyyyMMdd\HH\분류코드\품번_품명_카메라위치_HHmmssfff.ext
```

이 구조는 한 폴더에 파일이 과도하게 몰리는 문제를 줄이기 위한 구조다.

### 4. Pass/Fail 판정

최종 Pass/Fail은 다음 조합으로 판단한다.

```text
AI/Vision 결과
  + 품번 DB의 기준값/허용값
  + 위치별 측정값
  -> 최종 Pass/Fail
```

등록 기준 이미지와 현재 이미지를 직접 비교하는 방식은 아직 공식 판정 기준으로 두지 않는다.

이유:

- 기존 VLAD_Ops에서 제품별 기준 이미지 직접 비교 로직은 확인되지 않았다.
- 기준 이미지 비교는 조명, 배율, 회전, 카메라 위치, ROI 정의에 민감하다.
- AI 담당자가 image-to-reference matching 알고리즘과 허용 기준을 정의해야 한다.

### 5. 기준 이미지가 없는 경우

기준 이미지가 없으면 UI에는 “기준 이미지 없음”을 명확히 표시한다.

검사 자체는 AI/측정값 판정으로 진행할 수 있지만, 운영 기준에 따라 다음 중 하나를 선택해야 한다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 기준 이미지 없어도 검사 허용 | 초기 DB 구축 중에도 검사 가능 | 작업자 확인성이 낮음 |
| 기준 이미지 없으면 검사 차단 | 운영 품질 기준 명확 | 초기 등록 작업이 번거로움 |

현재 권장 기준은 “초기 개발/검증 단계에서는 검사 허용 + 경고 표시”, 양산 운영 전에는 “기준 이미지 없음 차단 여부”를 다시 결정하는 것이다.

### 6. VLAD_Ops의 이벤트 저장 방식 적용 여부

VLAD_Ops처럼 NG 또는 이벤트 발생 시 별도 Event 이미지를 추가 저장하는 것은 가능하다.

다만 현재 프로젝트에서는 기본 검사 캡처 이미지를 먼저 저장하고, 필요하면 그 위에 Event/NG 표시 이미지를 추가 저장하는 방식이 안전하다.

```text
DB\History\...\Original
DB\History\...\Event
```

같은 구조를 검토할 수 있지만, 기존 VLAD_Ops 코드에서 Original/Event 파일 저장 경로가 의도와 다르게 사용될 가능성이 있는 코드가 확인되므로 그대로 복사하지 않는다.

## 앞으로 판단이 필요한 항목

| 항목 | 필요한 결정 | 추천 기준 |
| --- | --- | --- |
| 기준 이미지 없음 처리 | 검사 허용/차단 여부 | 개발 중 허용, 양산 전 재결정 |
| AI 입력 방식 | 파일 기반 Mat 변환 유지 또는 실시간 Mat 직접 전달 | 현재는 파일 기반 유지, 성능 이슈 발생 시 직접 전달 추가 |
| 기준 이미지 비교 | 공식 판정에 포함할지 여부 | AI 담당자 알고리즘 확정 전까지 제외 |
| 이벤트 이미지 | NG 시 별도 draw 이미지 저장 여부 | History 원본 저장 후 Event 이미지 추가 저장 |
| History 보관 | 기간/HDD 기준 자동 삭제 정책 | 별도 보관 정책 UI 또는 설정 파일 필요 |

## 현재 적용 기준

2026-06-11 기준으로 현재 프로젝트의 적용 기준은 다음과 같다.

- `검사 시작` 시점에 새로 캡처한 이미지만 공식 검사 이미지로 사용한다.
- 공식 검사 이미지는 `DB\History`에 저장하고, UI에도 같은 이미지를 표시한다.
- `기준 이미지 저장`은 검사 이미지 저장과 별도이며, `DB\Image`의 제품 마스터 이미지를 갱신하는 동작이다.
- 기준 이미지가 없으면 UI에 “기준 이미지 없음”을 표시한다.
- Pass/Fail은 기준 이미지 픽셀 비교가 아니라 AI 결과와 DB 기준값/허용값 비교를 기준으로 한다.
- VLAD_Ops의 실시간 callback 구조는 영상 수신/AI 추론 구현의 참고 기준으로 사용하되, 현재 프로젝트의 이력/DB/품번 판정 구조를 대체하지 않는다.
