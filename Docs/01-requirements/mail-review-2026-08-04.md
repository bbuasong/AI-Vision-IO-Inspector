## 1. 핵심 결론

오늘 메일의 핵심은 새로운 기능을 대규모로 추가하는 것보다 현재 구현의 시작 지연, 처리 상태 가시성, 결과 상태 구분을 운영 가능한 수준으로 정리하는 데 있다.

1. OCR API는 버튼을 누를 때마다 실행하지 말고 프로그램 수명 동안 한 번 실행하여 재사용해야 한다.
2. 카메라 캡처 중에도 기존 스트리밍 화면을 유지하고, 팝업 대신 진행 상태를 카메라 패널 위에 표시해야 한다.
3. 제품 불일치와 시스템 오류를 같은 `Fail`로 처리하지 말고 `PASS / FAIL / ERROR`로 구분해야 한다.
4. 측정부 결과는 `True/False`가 아니라 측정값, 기준값, 허용오차, 단위, 판정을 표시해야 한다.
5. OCR로 읽은 품번이 DB에 없으면 검사 품목을 임의 선택하지 않고 부품 등록 흐름으로 연결해야 한다.
6. 다음 주 현장 기준정보 등록 일정이 있으므로 기준정보 등록, 이미지 등록, 측정부 등록의 정상 흐름을 우선 안정화해야 한다.

## 2. OCR 관련 메일 분석

### 2.1 메일 요청

메일에서는 첫 OCR 품번 인식 시간이 오래 걸리는 원인이 OCR 서버의 지연 기동인지 확인하고, 버튼 클릭 시 서버를 실행하는 구조라면 프로그램 시작 시 미리 실행해 달라고 요청했다.

### 2.2 현재 코드 확인 결과

현재 `MainWindowViewModel` 생성자에서 `RefreshOcrScanner()`를 호출하고, 이 호출은 `EpsonScanApiClient.GetScanners()`의 `EnsureStarted()`로 이어진다. 따라서 현재 버전은 OCR 버튼을 누를 때마다 `EpsonScanApi.exe`를 새로 실행하는 구조가 아니라 프로그램 초기화 과정에서 먼저 실행하고 이후 요청에 재사용하는 구조이다.

다만 `RefreshOcrScanner()`가 메인 창 표시 전에 동기 실행되므로 다음 문제가 남아 있다.

- OCR API와 보조 OCR 프로세스가 늦게 준비되면 메인 화면 표시가 함께 지연될 수 있다.
- API 시작 제한 시간이 60초이므로 장애 시 프로그램이 실행되지 않는 것처럼 보일 수 있다.
- 작업자는 `시작 중`, `준비 완료`, `오류` 상태를 구분하기 어렵다.

### 2.3 개선안

1. 메인 창을 먼저 표시한 뒤 OCR API를 백그라운드에서 한 번 선기동한다.
2. 옵션 OCR 화면에 다음 상태를 표시한다.
   - 중지
   - 시작 중
   - 준비 완료
   - 스캔 중
   - 오류
3. OCR 버튼은 API 프로세스를 실행하지 않고 준비된 API에 스캔 작업만 요청한다.
4. API가 비정상 종료되면 `Process.Exited`로 감지하고, 짧은 지연 후 한 번만 자동 재시작한다. 반복 실패 시 자동 재시작을 중단하고 오류를 표시한다.
5. 다음 구간을 별도 시간으로 기록해 병목을 구분한다.
   - OCR API 시작 시간
   - 스캐너 용지 취득 시간
   - 이미지 전처리 시간
   - OCR 판독 시간
   - DB 조회 시간
6. OCR 엔진에 첫 실행 준비 비용이 있다면 서버 준비 후 빈 스캔이 아닌 엔진 초기화만 수행하는 워밍업 API를 추가한다.

## 3. 카메라 캡처 관련 메일 분석

### 3.1 메일 요청

- 카메라를 순차 촬영할 때 표시되는 별도 팝업을 배포 버전에서 제거한다.
- 캡처 중 카메라 화면이 비거나 정지된 것처럼 보이지 않게 한다.
- 작업자가 처리 중인지 오류인지 구분할 수 있어야 한다.
- FFmpeg가 없을 때 긴 지연과 빈 화면이 발생한 현상을 점검한다.

### 3.2 현재 코드 확인 결과

현재 `VisionCameraCoordinator.CaptureVladRtsp()`의 기본 흐름은 RTSP를 다시 연결하지 않고 `VLAD_Rtsp_Info_Client_Registration()` 콜백이 보관한 최신 프레임을 저장한다. 따라서 정상 검사 경로는 메일에서 우려한 `검사마다 RTSP 재접속` 구조에서 이미 개선된 상태이다.

다만 다음 대체 경로가 남아 있다.

- 고해상도 채널은 원본 해상도 획득을 위해 `ConfiguredCameraService` 경로를 사용할 수 있다.
- 최신 콜백 프레임 저장 실패 시 `ConfiguredCameraService`로 복구한다.
- 이 하위 구현에는 FFmpeg, LibVLC, OpenCvSharp 순서의 캡처 경로가 남아 있다.

따라서 FFmpeg 누락 현상은 정상 콜백 경로와 대체 경로를 구분해서 로그를 남겨야 원인을 정확히 판단할 수 있다.

### 3.3 개선안

1. 검사 중에도 카메라 UI의 스트리밍 `ImageSource`를 교체하거나 비우지 않는다.
2. 카메라 화면 위에 반투명 상태 오버레이만 표시한다.
   - 캡처 대기
   - 캡처 완료
   - 추론 중
   - 완료
   - 오류
3. 순차 캡처 팝업은 제거하고 상세 정보는 로그와 옵션 상태 화면에 남긴다.
4. 디버그용 미리보기가 필요하면 `DEBUG` 빌드 또는 설정값에서만 명시적으로 활성화한다.
5. FFmpeg는 정상 콜백 캡처의 필수 구성요소가 아니라 원본 해상도 및 복구 경로의 배포 의존성으로 명확히 정의한다.
6. 프로그램 시작 시 FFmpeg, LibVLC, OpenCvSharp 등 대체 캡처 의존성을 한 번 점검하고 누락 항목을 옵션 상태에 표시한다.
7. 캡처 실패 시 여러 대체 방식을 장시간 연속 시도하지 말고, 카메라별 사용 경로와 제한 시간을 로그에 명시한다.

## 4. 검사 결과 상태 개선

메일에서는 검사 오류와 제품 불일치가 모두 빨간색 `Fail`로 표시되어 구분되지 않는 문제를 지적했다.

권장 상태는 다음과 같다.

| 상태 | 의미 | 색상 |
|---|---|---|
| `PASS` | 이미지 및 측정 기준 만족 | 초록색 |
| `FAIL` | 제품 불일치 또는 측정 기준 이탈 | 빨간색 |
| `ERROR` | 촬영, OCR, AI, 타임아웃, 파일 또는 런타임 오류 | 노란색 |

`NG`는 일반적으로 제품 불합격 의미로 사용되므로 시스템 오류 명칭으로 사용하면 현장 통계가 혼동될 수 있다. 고객이 반드시 `NG`를 요구하지 않는다면 `ERROR` 또는 `검사 오류`가 더 적절하다.

DB와 CSV에도 다음 값을 분리해서 저장해야 한다.

- 최종 상태
- 이미지 판정
- 측정 판정
- 오류 코드
- 오류 메시지
- 사용한 검사 엔진과 모델 버전

## 5. 측정부 결과 표시

메일 요구대로 측정부 결과는 `True/False`가 아니라 숫자로 표시해야 한다.

필수 표시값은 다음과 같다.

- 측정부 번호
- 항목
- 측정값
- 기준값
- 허용오차 하한/상한
- 단위 `mm`
- 판정

AI 결과에 측정값이 없으면 `False`로 대체하지 않고 값은 `-`, 상태는 `ERROR`, 메시지는 `측정값 미수신`처럼 구분한다.

## 6. OCR 미등록 품번 처리

1. OCR API가 반환한 상태와 품번은 자체 재판정하지 않고 그대로 표시한다.
2. 품번이 DB에 있으면 검사 대상 품목으로 선택한다.
3. 품번이 DB에 없으면 `미등록 품번`을 안내한다.
4. 사용자 확인 후 부품 등록 탭으로 이동하고 OCR 품번만 입력한다.
5. Search DB의 현재 선택 품목과 부품 등록 편집 품목은 서로 독립적으로 유지한다.
6. OCR 실패 이미지와 JSON은 원인 확인이 가능하도록 보존하고 다음 성공 또는 보존 정책에 따라 정리한다.

Vision 임시 판정과 AI 판정을 이력에서 혼합하지 않도록 검사 엔진 종류와 모델 버전을 반드시 저장해야 한다.

## 8. 확인이 필요한 사항

1. 시스템 오류의 화면 명칭을 `NG`가 아니라 `ERROR`로 사용해도 되는지 고객 확인이 필요하다.
2. 미등록 품번 인식 시 자동으로 등록 탭으로 이동할지, 안내 후 사용자가 선택할지 확정해야 한다. 권장안은 사용자 확인 후 이동이다.
3. 다음 주까지 필요한 `기준정보 등록 완료`의 최소 합격 기준을 품목 정보, 6장 이미지, 측정부 좌표, DB 저장으로 확정해야 한다.
4. OCR API 비정상 종료 시 자동 재시작 횟수와 수동 복구 방법을 정해야 한다.
5. FFmpeg를 배포 필수 파일로 둘지, 고해상도·복구 기능을 사용하지 않을 경우 선택 파일로 둘지 배포 정책을 확정해야 한다.

## 9. 권장 검증 시나리오

1. 프로그램 실행 직후 UI가 먼저 표시되고 OCR 상태가 `시작 중`에서 `준비 완료`로 바뀌는지 확인한다.
2. 첫 OCR과 두 번째 OCR의 각 처리 시간을 비교한다.
3. OCR API를 강제 종료한 뒤 한 번만 자동 복구되고 UI가 멈추지 않는지 확인한다.
4. 검사 중 6개 카메라 화면이 계속 갱신되고 상태 오버레이만 바뀌는지 확인한다.
5. FFmpeg를 제거한 배포 폴더에서 정상 콜백 캡처와 대체 경로 오류가 명확히 구분되는지 확인한다.
6. 제품 불일치, 측정값 이탈, 카메라 실패, AI 타임아웃을 각각 발생시켜 `FAIL`과 `ERROR`가 분리되는지 확인한다.
7. OCR 미등록 품번이 부품 등록 화면의 품번으로 전달되며 Search DB 선택 상태를 변경하지 않는지 확인한다.

## 10. 2026-08-04 적용 결과

적용 대상은 `Codes/Version1_1_0_0/AI-Vision IO Inspector`이다.

1. 메인 ViewModel 생성자에서 실행하던 OCR 장치 조회를 제거했다.
2. 메인 창 `Loaded` 이후 OCR API와 Epson ES-C320W를 백그라운드에서 준비하도록 변경했다.
3. 옵션 OCR 상태를 `시작 대기`, `시작 중`, `준비 완료`, `스캔 중`, `오류`로 구분했다.
4. OCR API 통신 실패와 USB 스캐너 미연결을 구분할 수 있도록 초기화 예외를 UI까지 전달한다.
5. 검사 작업의 `조회`, `캡처`, `추론`, `측정`, `판정`, `저장` 단계를 이벤트로 UI에 전달한다.
6. 검사 중에는 캡처 정지 이미지를 RTSP 영상 위에 덮지 않고 카메라 스트리밍과 상태 오버레이를 유지한다.
7. 검사 이력의 내부 `Ok/Ng/Error` 표기를 화면과 CSV에서 `PASS/FAIL/ERROR`로 통일했다.
8. 오류 카메라 테두리와 상태 색상을 빨간색 제품 불합격과 구분되는 노란색 계열로 변경했다.
9. OCR 미등록 품번은 사용자 확인 후 부품 등록 탭으로 이동하고 품번을 신규 입력란에 전달한다.
10. Search DB의 검사 품목 선택 상태는 OCR 미등록 품번의 등록 화면 이동과 독립적으로 유지한다.
11. 프로그램 종료 초기에 OCR 서비스를 먼저 해제하여 Vision 종료가 지연되어도 `EpsonScanApi.exe`가 남지 않도록 했다.
